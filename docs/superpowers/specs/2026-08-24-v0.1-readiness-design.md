# Josh Room v0.1 Readiness Design

## Goal

Make the existing Josh Room baseline safe for large JAT snapshots and reproducible enough to qualify as a v0.1 candidate without adding product features.

## Scope

The v0.1 readiness gate has five parts:

1. Stream snapshot payload, envelope, ciphertext, decryption, and local/R2 object transfer through files with bounded chunks.
2. Make `josh-room setup` an explicit host-only lifecycle step while the Room consumes read-only config and host Secret Service access.
3. Prove the exact published Room of Requirement `secure` image in a clean container and record its immutable digest.
4. Pin an immutable release tuple for the Room image, Josh Room, JAT, and RCC.
5. Require the existing Josh Room CI job on public `main` after the candidate tree is published and green.
6. Publish `templates/room` as the narrow OCI Dev Container Template `ghcr.io/joshyorko/josh-room/templates/room`.

No tag or release is created by this project. RCC Environment Artifacts, Actions, Hive orchestration, extensions, daemons, and new providers remain out of scope.

## OCI Dev Container Template

The existing `templates/room` directory is the complete publishable unit. A dedicated workflow validates its manifest and devcontainer JSON on pull requests and runs `devcontainer templates publish --registry ghcr.io --namespace joshyorko/josh-room/templates templates/room` on public `main`. Permissions are limited to `contents: read` and `packages: write`.

The workflow publishes only this template. It does not copy Room of Requirement image builds, Brewfiles, maintenance, release automation, or broad template matrices into Josh Room. Template versioning remains in `devcontainer-template.json`; the workflow checks semantic version shape and reports the exact OCI URI/version. Standard Dev Container tooling remains the user entrypoint. Josh Room does not add a DevPod launcher command.

## Root DevPod entry

The repository root `.devcontainer` is the personal Josh Room, not a separate development-only environment. `devpod up github.com/joshyorko/josh-room --ide vscode` clones the repository, discovers the root devcontainer, starts the digest-pinned Room of Requirement image, mounts host Josh Room config and Secret Service access, runs the same capability-only bootstrap as the published template, and exposes the existing `Josh: Enter Room` task. Root and `templates/room` devcontainer/bootstrap files remain byte-identical so the direct-repository and OCI-template entry paths cannot drift.

## Streaming architecture

The on-disk formats do not change:

- JAT payload remains `payload.haul.tar.zst`.
- Envelope remains an uncompressed tar containing exactly `manifest.json` and `payload.haul.tar.zst`, both regular files with mode `0600`.
- Manifest remains canonical `format_version: 1` JSON with payload size and SHA-256.
- Snapshot object remains age ciphertext stored at `objects/sha256/<ciphertext-sha256>`.
- Catalog remains bounded encrypted JSON and may continue using bytes APIs.

New file-oriented primitives sit beside compatibility bytes wrappers:

- `encrypt_file(source, recipients, output)` and `decrypt_file(source, identities, output, max_bytes)`.
- `build_envelope_file(manifest, payload, output)` and `read_envelope_file(envelope, payload_output)`.
- `ImmutableLocalStore.put_file(path)` and `download_file(key, destination, expected_digest, expected_size)`.

`create_snapshot()` computes payload metadata incrementally, writes the envelope directly to a restrictive temporary file, streams it through age, computes ciphertext metadata incrementally, and publishes the ciphertext file. `hydrate()` downloads ciphertext to its adjacent owned stage, decrypts to an envelope file, extracts the payload member incrementally to the JAT haul path, and invokes JAT Restore. No snapshot-sized `bytes`, `BytesIO`, or unrestricted read is allowed in these operation paths.

Compatibility bytes functions remain for small catalogs and existing callers, but are implemented over the file primitives where practical. Peak memory is bounded by a 1 MiB transfer chunk plus library overhead.

## Streaming acceptance

Unit tests reject snapshot-operation use of `Path.read_bytes`, `Path.write_bytes`, bytes-only store methods, and unbounded reads. A generated sparse payload test exercises a logical size of at least 1 GiB through envelope build/read with a guarded reader and verifies digest, size, layout, and bounded chunk requests. A secret/tool-gated real vertical continues to prove JAT, age, and R2 behavior; skipped gates remain skips.

## Host setup lifecycle

`josh-room setup` runs once on the Bluefin host. It stores R2 and age secrets in the host OS Secret Service and writes only non-secret metadata to `$XDG_CONFIG_HOME/josh-room/config.json`. The Room mounts that config read-only and brokers the host session bus. Normal Room commands never write config.

The host acceptance uses a temporary XDG config and synthetic keyring adapter to prove secret separation, file mode `0600`, and complete metadata from an initially absent config. Documentation must not imply setup runs inside the Room.

## Release tuple

`release-lock.json` is the machine-readable candidate tuple. It records:

- schema version and candidate version;
- immutable Room of Requirement image reference with digest;
- Room of Requirement source SHA;
- Josh Room source SHA used by bootstrap;
- JAT source SHA used by bootstrap;
- expected RCC version;
- the public repository URLs.

The personal template consumes the image by digest, installs Josh Room from its pinned Git SHA, fetches JAT at its pinned Git SHA, and fails closed if `rcc version` differs from the tuple. Tests require the template and lock to agree.

## Secure image evidence

A clean local container/devcontainer smoke must pull the digest-pinned `secure` image, run as the intended non-root user, execute the template bootstrap, and prove `josh-room doctor` can inspect the pinned JAT/RCC surface. If GHCR authentication or a published digest is unavailable, the gate is blocked rather than inferred from a tag.

## Branch protection

After the candidate commit is pushed and its public CI run succeeds, configure public `main` to require the exact observed CI check context and disallow non-fast-forward history. Read back the protection settings. Branch protection is not configured from guessed check names.

## Completion

v0.1 readiness is complete only when streaming tests, real local verticals, secure-image smoke, immutable tuple validation, OCI template publication/readback, public CI, and branch-protection readback all pass. Missing registry access, CI completion, or settings authority is a blocked gate, not passing evidence.
